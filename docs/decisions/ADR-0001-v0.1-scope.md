# ADR-0001: Scope of v0.1

**Status:** Accepted, 2026-11-18
**Source:** pro/con debate adjudicated by the lead, recorded at
`~/.kiro/crew/workspace/prep/ai-ml-engineer/REPO10-DEBATE-2026-11-18.md`
(Amit's local prep folder; not part of this repository).

## Context

The ask was "start working on repo 10 at production level for customer/user
usage readiness". The Phase 0 skeleton had four IR metrics, nine tests and
no git history. Two problems were verified before deciding anything: a
duplicate id in `retrieved` was counted at every position (recall could
exceed 1.0), and relevance was binary while the data people actually have
(TREC qrels, BEIR) is graded. Mature tools already exist: ranx (graded
qrels, paired tests), deepeval (LLM-judge CI gates), ragas.

## Decision

Build rageval to production quality, narrower than first proposed:

1. **Metrics first, provably correct.** Dedupe rule (first occurrence
   counts), graded gain for DCG/NDCG, `mrr@k`, and a per-query cross-check
   against ranx as a dev-only reference. Runtime dependencies stay empty.
2. **Then loaders, report and CLI** (JSONL, TREC qrels and run files; a
   versioned JSON report with bootstrap confidence intervals;
   `rageval run` / `rageval compare`).
3. **Then a non-inferiority gate** (`rageval gate`: fail unless the lower CI
   bound of candidate minus baseline per metric is above `-max_drop`) and a
   GitHub Action around it.
4. **Grounding check as an EXPERIMENT**, labelled so, with a calibration
   report against at least 50 human labels before any README claim.
5. **Public on GitHub at v0.1. No PyPI publish** until Amit says go, and
   preferably after one named consumer exists.

This ADR covers round 1 (item 1 plus hygiene). Items 2-5 are later rounds.

## Alternatives rejected

- **Full v0.1 product with PyPI release and a shipped grounding detector.**
  Rejected: ranx and deepeval already cover the niche, so publishing at
  v0.1 would duplicate maintained tools; a lexical grounding check is not a
  trustworthy detector (reference detectors report roughly 45% F1 on
  RAGTruth summaries) and would put a claim in the README the code cannot
  back.
- **Thin plugin over ranx or deepeval.** Rejected: ranx pulls numba, pandas
  and scipy into every user install; the value here is a dependency-free,
  ID-based metric core whose correctness is proven against ranx rather than
  inherited from it.
- **Metrics-only library, nothing else, ever.** Rejected: the portfolio
  claim "retrieval evaluation" needs an end-to-end harness and a CI gate to
  be true, and those are exactly what interviews probe.
- **Learning artefact only (no public repo).** Rejected: fails the "public
  with results" bar.
- **Significance-only regression gate.** Rejected in favour of
  non-inferiority: at ~50 queries a significance test has too little power
  and passes real regressions.

## Consequences

- `ranx` is a dev extra; a CI job fails if a user install brings any
  third-party package.
- Every metric definition is written down in `docs/METRIC-DEFINITIONS.md`
  and locked by `tests/test_ranx_crosscheck.py`.
- The README says what exists, not what is planned, and will not claim
  grounding detection until the calibration report exists.
- The 3.9/3.10 interpreters are dropped (end-of-life); CI runs 3.11-3.14.

## Reversal condition

Stop and reconsider if a maintained, dependency-free tool appears that
already ships ID-based metrics plus a CI gate with an exit code; or if Amit
cannot give the 10-15 review hours the plan assumes without pushing other
commitments back. Either case reopens the "thin layer over ranx" option.
